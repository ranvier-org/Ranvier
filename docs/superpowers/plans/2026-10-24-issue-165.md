## Current state (2026-10-24, `issue/164` tip `3037b141`)

- `TraceLog.Events` copies the whole `ResizeArray<TraceEvent>` under the log's lock. `Trace.events` and every query in `TraceApi.fs` go through that copy.
- Seqs are contiguous: `append` increments `clock` once per event, so `events[i].Seq = events[0].Seq + i`.
- The log reads its own events in two places: `OtherAt seq` (indexes `events[seq - 1]`; used for the first dirty `Mark` of a node, `Trace.fs` around line 1621) and `Describe id` (scans for the node's `NodeNew`, used in rerun-guard messages). Both assume the log starts at seq 1.
- Live bookkeeping (`openRuns`, `firstDirty`, `flights`, `settles`, `streams`, timed tables) stores seqs as ints and never dereferences an event, except through `OtherAt`.
- `Trace.origin`, `Trace.timing` and `Trace.reconcile` search the events for `NodeNew` / edge events, so a truncated prefix would hide them.
- `docs/maps/SignalMap.fs` reads with `Trace.events g` then `events[read..]` in `baseline` and `drain`.
- The #164 baseline records the incremental tail read as a full copy plus a slice (`bench/Ranvier.Benchmarks/Tracing.fs` `TraceQueryBenchmarks`, `bench/Ranvier.Counters/TraceGrowth.fs` `TailMs`).
- `docs/content/guide/tracing.md` "Limits" states there is no eviction or checkpoint API.

## Design

### API

Added to the `Trace` module under `#if RANVIER_TRACE`, graph first like `snapshotAt graph seq`:

```fsharp
/// Events with Seq > seq, oldest first.
val eventsSince : graph: Graph -> seq: int -> TraceEvent[]
/// Folds the events up to and including seq into the checkpoint named name, and drops them from the log.
val checkpoint : graph: Graph -> seq: int -> name: string -> unit
/// The log's checkpoint: its name (null before any checkpoint) and the snapshot folded from the dropped events.
val checkpointOf : graph: Graph -> TraceCheckpoint
```

`TraceCheckpoint = { Name: string; Snapshot: TraceSnapshot }`, with `Snapshot = TraceModel.emptySnapshot` and `Name = null` before the first checkpoint, so `Snapshot.Seq` is always the last dropped seq. A record matches `TraceOrigin` / `TraceHistory`; `checkpointOf` is total, which avoids an option every consumer would unwrap with the empty snapshot anyway. `Ranvier.CSharp` `Tracing` gains `EventsSince`, `Checkpoint` and `CheckpointOf` in the same shape as `Events`.

Why these shapes: the issue's illustrative `Trace.eventsSince graph sequence` and `Trace.checkpoint graph sequence name` already follow the module's convention (graph, then position), so they are kept. A query over checkpoint state needs a name distinct from the operation; `checkpointOf` follows `logOf`.

### Cursor semantics

A cursor is the seq of the last event the consumer has read; 0 reads from the start.

| Cursor `c` | `eventsSince graph c` |
| --- | --- |
| `c < 0` | `ArgumentOutOfRangeException` |
| `checkpoint.Seq <= c <= last seq` | events with `Seq > c`, oldest first; empty at `c = last seq` |
| `c > last seq` (future) | `ArgumentOutOfRangeException` naming the last seq |
| `c < checkpoint.Seq` (expired) | `ArgumentOutOfRangeException` naming the checkpoint seq |

An expired or future cursor is a consumer bug or a missed resync, so it throws like `whyAt`'s run number, rather than returning a silently shorter suffix. A consumer resyncs from `checkpointOf graph` and `eventsSince graph (checkpointOf graph).Snapshot.Seq`. The read copies only the suffix: index `c - firstSeq + 1` into the `ResizeArray`, `CopyTo` of the remaining count, under the log's lock. It is not gated, like `Trace.events`: it reads the log under the same lock and allocates nothing on the graph.

### Checkpoint semantics

`Trace.checkpoint graph seq name` runs through `gate` (graph thread, no flush, discharge or run in progress; a `batch` is allowed), so no open walker frame or notification refers to an event it drops.

- `seq` must satisfy `checkpoint.Seq <= seq <= last seq`, else `ArgumentOutOfRangeException`. `seq = checkpoint.Seq` only renames.
- The log folds `TraceModel.fold checkpoint.Snapshot prefix` and stores it with `name`, then `RemoveRange (0, count)`. Dropping the events releases their `Payload` references (values, exceptions, sites, labels). The fold cannot run inside `TraceLog` (`TraceModel.fs` compiles after `Trace.fs`), so `TraceApi.fs` computes it and hands it to a `TraceLog.Truncate (seq, name, snapshot: obj)` member.
- `OtherAt` serves dropped seqs still referenced by `firstDirty` from a small table filled at truncation; every other dropped seq returns 0 as today's out-of-range case does.
- `Describe` falls back to a description table filled at truncation for nodes whose `NodeNew` was dropped.

Queries over a checkpointed log use the checkpoint as the state before the first retained event:

- `snapshot graph = TraceModel.fold checkpoint.Snapshot tail`; `snapshotAt graph s` folds the tail up to `s` and throws `ArgumentOutOfRangeException` for `s < checkpoint.Seq`.
- `why`, `whyAt`, `whyDepth`, `history` pass `checkpoint.Name` instead of `null`, so a cause before the first retained event resolves to `BeforeCheckpoint name` (the existing semantics).
- `origin` falls back to the snapshot node (kind, owner, label, path, site, created seq) when its `NodeNew` was dropped; `Run` is 0 there, documented as before the checkpoint. `timing` checks the snapshot node's kind. `reconcile` compares against `snapshot.Sources` / `snapshot.Observers` instead of folding the edge events alone.
- `dumpText` / `dump` write `checkpoint.Name`, `checkpoint.Snapshot` and the tail: the existing schema already describes a dump that starts after seq 1.
- `whyNot` and `waitingOn` read only the tail; a reason or flight older than the checkpoint is reported as absent, documented on each.

### Consumer migration

`SignalMap.fs` keeps `read` as the last consumed seq: `baseline` calls `Trace.eventsSince g 0`, `drain` calls `Trace.eventsSince g read` and sets `read` to the last returned seq. No second consumption mechanism.

### Measurement

`TraceQueryBenchmarks` gains `EventsSince` beside the copy-and-slice row at the same history lengths, and `TraceGrowth` gains a `SinceMs` column beside `TailMs` plus a checkpointed variant of the `memo` workload that checkpoints at each probe point and reports retained heap. The comparison is against `docs/.ai/benchmarks/tracing/f48a3a7/`: the cursor read stays flat across 1,000 to 100,000 updates where the slice grows linearly, and the checkpointed run's retained heap stays bounded.
