# Issue #184: Input journal and replay for untraced and traced builds

Branch `issue/184`, cut from `integration/issues` at `dd8bff65` (#166 merged). Split from #65 by
`docs/.ai/research/2026-10-24-issue-65.md` (on `issue/65`), option A, section 6.1, with the user's
answers in its section 8.

## Goal

An input journal that records a graph's external inputs in both builds, and a replay driver that
reproduces a run (diagnostic replay) or re-enacts it (re-enactment), without the traced build's cost.

## Acceptance criteria (copied from the issue)

1. A cart-sample test journals `Mvu` messages and external signal writes, replays them in diagnostic
   mode into a fresh traced graph, and the replayed final `Trace.snapshot` and the `Trace.why` output
   of every effect run equal the live traced run's.
2. A property test: for any sequence of external writes, settles and failures, replaying the journal
   into a fresh untraced graph yields the same values for every keyed input and every memo.
3. Re-enactment mode re-runs async work; a test shows a changed async result flows through replay.
4. Writes made by a running computation are not journaled; a test asserts it. An unregistered payload
   produces an entry marked non-replayable, and `replay` fails with a named error on it.
5. With `Journal = None`, paired counters (`bench/Ranvier.Counters`, interleaved in one run) show the
   untraced `signal` and `memo` steady-state scenarios within the noise interval of the baseline; the
   only IL difference reported by `tools/verify-trace.fsx` is the guarded hook, listed in the PR.
6. Snapshot plus tail: restoring a #68 snapshot taken at a journal position and replaying the later
   entries equals an uninterrupted run (once #68's format exists).
7. Fable: the replay test passes under `build.fsx -- test-fable`. User-facing docs cover the journal,
   both replay modes and restore.

**User ruling (2026-10-24):** criterion 6 depends on #68's stored-state format, which has no implement
issue yet. Every other criterion is built; criterion 6 is recorded as waiting on #68 in the PR body
and the PRIORITIES log. No snapshot format is invented here. The docs' restore section states the
contract the journal offers #68 (entry `Seq` is the journal position) and that restore lands with #68.

## Core and view state

This is core work (`src/Ranvier`, both builds) plus `src/Ranvier.Elmish`. No `Ranvier.View` code
changes.

**Core primitives used:**

- `Graph` and its dispatcher (`Graph.Dispatch`, `RequestFlush`, the flush pass): replay applies each
  entry on the graph thread and flushes at each journaled flush boundary, so replay schedules work
  exactly as the live run did.
- `Signal<'T>` setter and `AsyncSource<'T>.Settle` / `Fail`: the input sites the hook observes.
- The graph's running-computation state: tells an external write from a derived one.
- `Mvu` `Dispatch` / `Apply`: the message site.
- `Trace.snapshot` / `Trace.why` (traced build): the oracle for criterion 1.

**View-owned state:** none.

## Design

### Types (in `Types.fs`, before `GraphOptions`; functions in a new `src/Ranvier/Journal.fs` after `Api.fs`, both builds)

```fsharp
type JournalEntryKind = Write | Settle | Fail | Message | Flush

type JournalPayload =
    | Empty                                              // Flush
    | Encoded of codec: string * version: int * data: string
    | NonReplayable of payloadType: string               // unkeyed node, or no codec

type JournalEntry =
    { Schema: int            // 1
      Stream: string         // IInputJournal.Stream
      Seq: int               // 1-based, per graph; the journal position #68's snapshot records
      Kind: JournalEntryKind
      Key: string option     // the application key; None for an unkeyed node and for Flush
      PayloadType: string    // the CLR / Fable type name of the value
      Payload: JournalPayload }

type IInputJournal =
    abstract Stream: string
    abstract Record: entry: JournalEntry -> unit
```

`GraphOptions.Journal: IInputJournal option`, default `None`, with `WithJournal` matching the
existing `With*` members, and a fifth line in `ToString` (AotSmoke text updated).

### Keys and codecs

- `JournalCodec<'T> = { Name: string; Version: int; Encode: 'T -> string; Decode: string -> Result<'T, string> }`,
  a record of functions as `TraceCodec` is. Core keeps no `Ranvier.Wire` reference; a `WireCodec<'T>`
  plugs in as `{ Name = ..; Version = ..; Encode = wire.Encode; Decode = wire.Decode >> Result.mapError string }`,
  shown in the docs and used by the tests (the test projects reference both).
- `Journal.key (key: string) (codec: JournalCodec<'T>) (signal: Signal<'T>) : Signal<'T>` and the
  `AsyncSource<'T>` overload register the node on its graph's journal and return it. A no-op when the
  graph's `Journal` is `None`. A duplicate key on one graph raises `ArgumentException` naming it.
- **Key space:** the key is an application string, the key #68's `StoredRecord` will use, so #166's
  stable node key and #68's application key are one key space. It is a separate API from the trace
  `Named` path because the journal must work in the untraced build, where trace paths do not exist.
  In the traced build `Journal.key` also writes the key as the node's trace label when the node has
  none, so a traced dump shows the same name.

### Recording

- The graph resolves `options.Journal` once into a nullable internal field (`journal`), plus a
  bindings table `Dictionary<int, JournalBinding>` and a seq counter, allocated only when a journal is
  present.
- **Hook sites** (the only untraced IL change; each is one field load and a null check):
  1. `Signal<'T>.Value` setter, before the equality cutoff (an equal write is still recorded, since
     the traced log records it too and replay must reproduce its seq).
  2. `AsyncSource<'T>.Settle` and `Fail`, inside the posted body, so the entry order is the
     graph-thread order.
  3. The end of a flush pass, recording a `Flush` entry when any entry was recorded since the previous
     boundary. Replay flushes at each boundary, so batching matches the live run.
- **Derived inputs are skipped:** a write or message made while a computation runs (memo, effect,
  async-memo body, including under `untrack`) is not recorded; nor are writes made inside a journaled
  `Mvu` message's `Apply` and its synchronous commands. The check uses the graph's run state, not
  `current`, because `untrack` clears `current`.
- `WriteExcept` is only called by a running computation, so it carries no hook.
- An unkeyed node, or a keyed node whose `Encode` raises, records `NonReplayable payloadType`; the
  entry is never dropped.

### Mvu

`Mvu.journal (key: string) (codec: JournalCodec<'Msg>) (mvu: Mvu<'Model, 'Msg>)` registers the
message site. `Dispatch` from outside a computation records a `Message` entry before `Apply`, then
runs `Apply` and the synchronous commands with recording suppressed (the root write and the commands'
writes are derived from the message). A later message dispatched by an async command is a new
external message and is recorded. Ranvier.Elmish reaches the hook through `InternalsVisibleTo` from
`Ranvier` if the assembly already grants it, and otherwise through a public
`Journal.registerSite` / `Journal.recordMessage` / `Journal.derived` set that any adapter can use.

### Replay

```fsharp
type ReplayMode = Diagnostic | Reenact
type JournalReplayException(seq: int, key: string option, reason: string) = inherit exn
Journal.replay (mode: ReplayMode) (graph: Graph) (entries: JournalEntry seq) : unit
Journal.replaying (graph: Graph) : ReplayMode option
```

- Runs on the graph thread (same contract as a signal write; off-thread callers use `Graph.Dispatch`),
  applies entries in `Seq` order, and calls the graph's flush at each `Flush` entry.
- `Write` decodes through the key's codec and writes the signal; `Message` decodes and dispatches
  the `Mvu`; `Settle` / `Fail` settle or fail the source in `Diagnostic` mode and are skipped in
  `Reenact`, where the application's async work runs again (gateways read `Journal.replaying` to skip
  external calls in `Diagnostic` mode).
- Fails with `JournalReplayException`, naming the seq, key and payload type, on a `NonReplayable`
  entry, a key not registered on the target graph, a codec name or version mismatch, or a decode
  error. `Fail` entries carry the exception's type and message as the payload, and replay raises a
  `JournalReplayedFailure` (message preserved) into the source.
- `MemoryJournal(stream)` is the in-memory `IInputJournal` (an `Entries` list) for tests and samples.

### Scope decisions

- **Async memos are not journal sites.** The research note's site table lists `AsyncSource` settles as
  the async input; an async memo's flight is a computation over journaled inputs. Diagnostic replay
  of a graph whose async memos call external services re-runs them unless the application routes the
  result through a keyed `AsyncSource` (documented). Substituting async-memo flights is a follow-up.
- **No JSON form in this issue.** Entries are F# records; a JSONL writer belongs with the #65 export
  sink or #68.
- **Seq is the journal position.** #68's snapshot will record a `Seq`; replaying entries with a greater
  `Seq` after restore is the tail. Criterion 6 waits on #68 (user ruling).

## Decisions

- **Application key, not trace path.** The trace `Named` path does not exist untraced; the journal
  needs a key in both builds, and it must be #68's key. `Journal.key` takes the string and mirrors it
  into the trace label when traced.
- **Codec as a record of functions.** Matches `TraceCodec`; keeps `src/Ranvier` free of a
  `Ranvier.Wire` reference (the two packages pin different `System.Text.Json` versions). A
  `WireCodec<'T>` adapts in one expression.
- **Flush boundaries are journaled.** Without them a replay cannot reproduce batching, and the
  traced `why` output of criterion 1 would differ.
- **Equal writes are journaled.** The traced log records them; skipping them would shift trace seqs.
- **Criterion 6 deferred to #68** by user ruling.
