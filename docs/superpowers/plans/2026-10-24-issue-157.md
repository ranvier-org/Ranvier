# Issue #157: payload-direct Arms.Match lowering under Fable

Issue: [#157](https://github.com/shayanhabibi/Ranvier/issues/157) perf(arms): restore the 5% Chromium overhead target.
Branch `issue/157`, cut from `integration/issues`. Spec: [`2026-10-21-arms-match-design.md`](../specs/2026-10-21-arms-match-design.md),
Phased implementation 8. Measurements: [`docs/research/2026-10-21-arms-match.md`](../../research/2026-10-21-arms-match.md),
"Payload-direct spike".

## Goal

Under Fable, `Arms.Match` lowers to the payload-direct shape the spike measured: one `armOf` definition per target whose
instance is the arm's values thunk, a selector that returns `[target, pattern variables..., matched value, instance]`,
and readers that read `p ()[k]`. The Fable cells, `enter`, withdrawal and graph tags are removed. Each Chromium arm
operation's paired median returns to at most 1.05 against `ranvier-sugar`, with every existing behaviour, diagnostic and
parity check unchanged.

## Acceptance criteria (from the issue)

- Preserve plugin/.NET parity, diagnostics, helper-view splices, held exits and event handlers, counters, structural
  hashes, Strict hydration, concurrency, and Prepare behavior.
- Re-run paired Chromium timings on a quiet machine with matching source hashes, versions and load notes. Each
  create/switch/payload/clear median must be at most 1.05 against ranvier-sugar; report the bootstrap 95% intervals.
- Keep retained heap after create within 10%; report after-switch heap at both row counts. Keep first-site bundle at
  most 400 B gzip, later sites at most 60 B, and no cost for apps that do not use Arms.Match.
- Run the complete applicable .NET, Fable, DOM, Arms, browser, analyzer, formatting and trim gates, plus primitive
  instruction-count comparisons before merge.
- Update chromium-gate.mjs, the spec, plan and research note together; do not silently change thresholds to fit
  measurements.

**User ruling (2026-10-24), which overrides the 1.05 median criterion above for switch and payload:** accept and
document the concession on the Chromium budget. Create and clear keep 1.05. `armsSwitch1k` and `armsPayload1k` get
per-operation budgets: the upper bound of the pooled paired 95 % interval across this issue's committed runs, rounded
up to 0.01 (Decision P9). The plugin's output is indistinguishable from the hand-written spike shape
(`arms-match-shape.json`), and that is the reason. With `chromium-gate.mjs` passing on the committed results, this
criterion is met. The measured medians, intervals, CPU load and new budgets are recorded in the spec, this plan's Log,
the research note and `docs/content/view/arms.md`.

## Core and view state

**Core primitives used:**

- The arm memo behind `matchWith` (a memo with a comparer and an owner per selected arm): selection, remount versus
  update, and disposal of the outgoing arm. The key stays the target's definition; the same target keeps its arm and
  receives the new values array through its props accessor.
- The arm's props accessor (`unit -> 'props`), which the region already hands each arm: it is the body's instance in
  the new shape, so a reader, event handler or held reader reads its own arm's current values, as the `armOf` twin does.
- `Owner` cleanup and `Graph.TryCurrent` remain in use on .NET only (cells path, unchanged).

**View-owned state:**

- Under Fable: the site's definitions array, one `armOf` per target, built once per evaluation of the call. It is a
  template table. The per-site `WeakMap` of cells is deleted, so Fable sites hold no lookup state, except a site that
  passes a view to a helper over the concrete instance type (Decision P8).
- Under Fable, for a helper over the concrete instance type: a `WeakMap` from the site's tag and the instance to the
  helper's mounts per target, each holding its arm's values thunk and, after its cleanup, its last values. The helper
  passes the instance, not the arm's thunk, to the lambdas it receives, and the core has no owner-scoped lookup from
  which such a lambda could find its arm (spec Decision 13).
- On .NET: the cells table of spec Decision 13, unchanged (see Decision P1).

## Decisions

**P1. Payload-direct under Fable only; .NET keeps the quotation and cells path.** The Chromium gate measures the Fable
bundle only, and .NET renders on the server, where the per-read cost is the server-render figure already within the
twin. On .NET the body's instance type is a real generic argument: retyping a quoted body from `TemplateView<'inst>` to
`TemplateView<unit -> obj array>` re-instantiates every generic builder call in the quotation, the review's 3-week
estimate. Parity is defined by observable output, and the existing suites check it: server HTML and structural hashes
on both targets (`ArmsServerChecks.fs`, `arms-server.test.mjs`), Strict hydration of .NET HTML by the Fable client
(`arms-hydration.test.mjs`), and the diagnostic texts and ranges. This amends spec Decision 4 ("one runtime path"):
two runtime shapes behind one parity contract. The spec records the amendment in Step 10.

**P2. The selector returns one array, `[target, site tag, bound values..., matched value, instance]`.** The spike's shape
(`KeyedRowsSugarArrayPerf.fs`, `ArmsSizeEntries.arrayLoader`). The plugin emits a selector over `(instance, value)`;
`Site.direct` passes the array as the arm's props and indexes the definitions with element 0.

**P3. Every reader over the instance type in a body is rewritten**, not only those that reference a bound identifier:
its argument becomes the values thunk, so its instance parameter is bound to `p ()[last]` in the prologue. A lambda
or delegate over the instance that refers to no bound identifier and never uses its parameter gets no prologue.
A function over the instance bound in a body takes the thunk when it reads a pattern variable, and a reader's
application of it to the reader's instance passes the thunk; any other such function keeps the instance. A lambda over
the instance passed to a call outside Ranvier.View with a non-view result, such as `List.sortBy`, keeps the instance.
Each rewritten function has its own tag in its emitted names (`armsArm_[site]n[k]_...`, `armsRead_[site]n[k]`), so a
function Fable inlines into a reader declares no name twice. A reader of a site nested two or more levels deep carries
its path in its parameter name (`armsArm_[tag]_[site]x[index]...`), and each enclosing site extends it. A function bound
in a body returns views over the values thunk, so its applications are not spliced.

**P4. Instance-typed values that are not lambdas are adapted.** A function value of type `'inst -> 'v` in a body is
eta-wrapped (`fun p -> f (p ()[last])`). A `TemplateView<'inst>` value (a helper view) is spliced through an adapter
child `render adapter (fun p -> p ()[last])` whose instance is the enclosing instance again; the splice probe showed
that this keeps the structural hash and server HTML.
A call of a helper whose view is over the concrete instance type, rather than a type parameter, is spliced as well,
through `Site.spliceHeld` (Decision P8); a lambda over the instance passed to it receives the instance and reads its
pattern variables from `Site.heldValues (s, tag, target)`. The helper's other arguments receive the instance too: the
lambdas over the instance inside a view built in the body read `heldValues` for their instance, and a function or view
bound in the body receives `fun () -> heldValues (s, tag, target)` as its values thunk (a view through an adapter child).

**P8. A helper over the concrete instance type reads its arm's values through a lookup.** Each mount of the spliced
helper registers its arm's values thunk under the site's tag, the instance and the target, and on its cleanup records the
thunk's last values and withdraws. `heldValues` returns the first live mount's values, or else the last values of the
target's last withdrawn mount, as `Cells.values` does on .NET, so a held exit or a handler inside the helper reads its
own case's values after the instance moves to another target. The lookup and its `WeakMap` sit in
functions of `Site.fs` that only such sites import, so `size.mjs` measures the other sites unchanged.

**P5. AM006 stays.** A reader that receives a value other than its site's values thunk raises AM006 with the existing
texts (Release: the anchor text). The guard checks a site tag at a fixed position of the values array; its bytes are
measured against the 15-25 B estimate. Each site binds its tag, an empty object, at element 1 of its values arrays;
every read of a values thunk is `Site.values (thunk, tag)`, which raises AM006 unless the thunk is a function returning
an array with that tag. A nested reader's path checks each step against its site's tag. Measured with `size.mjs`: 14 B
gzip per later site, and 91 B on the first site (the runtime guard and the Release AM006 text), 183 B against the twin.

**P6. Public API is unchanged.** `Arms.Match (read, function ...)` and `Arms.Prepare ()` keep their signatures on both
targets. The plugin's `lowered` argument changes shape; it is internal to the plugin and the runtime.

**P7. Timings run on the shared machine and are judged by the paired interval.** The issue asks for a quiet machine;
the machine is shared by up to three lanes and is never quiet, so its load is the baseline. `keyed-rows.mjs` already
interleaves the candidate and `ranvier-sugar` in each round, so the paired median ratio and its bootstrap 95 % interval
carry the verdict, with CPU load recorded before and after the run. The 1.05 budget is unchanged.

**P9. Per-operation Chromium budgets for switch and payload (user ruling).** `chromium-gate.mjs` holds a budget per
operation: `armsCreate1k` and `armsClear1k` 1.05; `armsSwitch1k` and `armsPayload1k` the upper bound of the pooled
paired interval, rounded up to 0.01, as constants with a comment naming the runs they come from. The committed runs
are `docs/.ai/benchmarks/arms-157-noisy-probe.json` (8ee10018), the Step 11 run (299ab276, kept as
`docs/research/arms-match/arms-match-299ab276.json` when `arms-match.json` is refreshed), the
`ranvier-arms-match:ranvier-sugar` pairs of `arms-match-shape.json` (fccc740c) and the refreshed `arms-match.json`.
Pooling concatenates each run's per-pair ratios (`ranvier-arms-match` over `ranvier-sugar`, same replicate and round)
and takes the percentile bootstrap of their median with the method of `keyed-rows.mjs` (10,000 resamples, fixed
seed, 2.5 and 97.5 percentiles). A script `experiments/Ranvier.View.Arms/Checks/pooled-interval.mjs` prints the pooled
median and interval per operation, so the constants can be rederived; the gate reads only `arms-match.json`, as
before. The budget is fixed from the measurements, not refitted per run; a later run whose median exceeds it fails.

## Steps

Each step is one commit, test first. Gates named per step are the ones it touches; Step 12 runs them all.

1. **Parity characterisation of the array shape.** Add the spike's hand-lowered loader (`ArmsSizeEntries.arrayLoader`
   shape) to the Arms checks and assert, in `arms-server.test.mjs`, that its server HTML and structural hash equal the
   `Arms.Match` loader's and the twin's for the three states, and, in `arms-hydration.test.mjs`, that it hydrates the
   .NET golden HTML under Strict. Guards P1 before any lowering change.
2. **`Site.direct` and the plugin's array selector and lambda readers.** Fable runtime: `Site.direct read select
   definitions` (P2), `Arms.Match`'s Fable branch calls it. Plugin (`Lower.fs`): selector over `(instance, value)`
   returning the array; every lambda and delegate over the instance rewritten with a `p ()` prologue (P3); bound
   identifier `i` read as `a[i + 1]`, the instance as `a[last]`. Red: update `Tests/expected/Sites.js` and
   `prologues.txt` to the new shape, then make `PluginTests.fsx`, `arms.test.mjs` (nine-step traces equal the twin's)
   and `arms-counters.test.mjs` pass.
3. **Function-valued readers.** Fixture: a body that passes a named `'inst -> string` function as a text reader and as
   an attribute reader. Red in `arms.test.mjs`; eta-wrap per P4.
4. **Helper splices.** Fixture `helper` (a `TemplateView<'inst>` helper inside a body, and the generic helper over a
   reader). Red on the mounted trace and on the server hash; splice through the adapter child per P4; the hash and
   HTML equal the .NET path's.
5. **Nested sites.** Fixture: an inner `Arms.Match` over the same instance inside an outer body, its reader reading an
   outer pattern variable. Each site owns its values array; traces equal the twin's.
6. **AM006 guard.** Fixture: a reader over the instance type that receives a row item of the instance type (spec Risk
   3). Red: the Debug and Release texts in `arms-debug.test.mjs` and `arms.test.mjs`; add the tag check per P5.
7. **Remove the Fable cells.** Delete the `FABLE_COMPILER` branch of `Cells.fs` and the Fable arm of `Site.create`;
   the .NET path is untouched. `size.mjs`: first site at most 400 B gzip, each later site at most 60 B, the
   no-`Arms.Match` entry 0 B; record `docs/research/arms-match/bundle.json`.
8. **Held exits, event handlers, Twice, pending sources, Debug build.** Re-run Testing 4, 5, 8, 9 and 10 on the new
   shape; add a fixture only where an existing one does not cover the payload-direct path (held reader reads its own
   row's props).
9. **Heap.** `keyed-heap.mjs --fixture=arms` after create and `--after=switch` at 1,000 and 10,000 rows. Extend
   `chromium-gate.mjs` to report the after-switch heap at both counts beside the after-create 10 % gate.
10. **Gate, spec, plan and research note together.** `chromium-gate.mjs` budget 1.12 -> 1.05 (the original target, not
    a fit to measurements); spec Testing 11, Decision 4 amendment (P1) and Phased implementation 8 marked done; the
    2026-10-21 plan's Ruling 38 noted as superseded; research note sections "Chromium", "Heap", "Bundle" rewritten for
    the new shape. The gate fails until Step 11's results land.
11. **Paired Chromium timings on the shared machine.** `keyed-rows.mjs --modes=ranvier-sugar,ranvier-arms-match
    --ops=armsCreate1k,armsSwitch1k,armsPayload1k,armsClear1k --processes=3 --rounds=15
    --pairs=ranvier-arms-match:ranvier-sugar` through `gate-lock.ps1 bench`; record CPU load before and after, source
    hashes, tool versions and load notes in `arms-match.json`; report the paired median ratios and their 95 %
    intervals. The busy machine is the baseline: the paired interleaving cancels shared load. An op whose interval
    lies below 1.05 meets the budget; one whose interval lies above it is a finding fixed before Step 12; one whose
    interval straddles 1.05 is recorded as straddling in the results, the research note and the gate output, and the
    work continues. The untracked `arms-157-noisy-probe.json` from the interrupted iteration is committed with this
    step as an earlier probe and is superseded by the Step 11 run.
12. **Full gates.** `dotnet fsi build.fsx -- test` and `-- test-fable`, Playground `npm run test:arms`,

13. **Refresh `arms-match.json`.** Copy the Step 11 run to `arms-match-299ab276.json`, then one paired run with the
    Step 11 command through `gate-lock.ps1 bench`, CPU load (three readings) before and after in its notes, source

14. **Pooled interval and per-operation budgets.** Red: `chromium-gate.mjs` with per-operation budgets reads a
    `budgets` table; `pooled-interval.mjs` over the four committed runs (P9) prints the pooled medians and intervals;
    set switch and payload to the upper bounds rounded up to 0.01, create and clear 1.05. Green: the gate passes on
    the committed results.
15. **Record the concession.** Spec Testing 11 and Phased implementation 8, this plan's Log, the research note
    "Chromium" section and a "Cost" paragraph in the `Arms.Match` section of `docs/content/view/arms.md`: per-run and
